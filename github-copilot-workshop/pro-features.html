Copilot Instructions

10 minutes

Copilot Instructions help you customize how Copilot generates code and reviews your work. They're essential for maintaining consistency across your team.

What are Custom Instructions?

Instructions are project-wide guidance stored in a single file that Copilot automatically reads on every request in that repository. Unlike a one-off prompt, they don't need to be retyped — once the file exists, every conversation and every teammate benefits from the same baseline.

Think of instructions as the "house rules" for your project: standing guidance that should apply no matter what you ask Copilot to do, such as:

  • Enforcing a coding style or language/framework preference
  • Documenting architecture conventions (folder structure, layering)
  • Setting security rules (no hardcoded secrets, validate all input)
  • Establishing testing expectations (coverage, frameworks to use)

Setting Up Instructions

Create a file at .github/copilot-instructions.md in your repository:

# Copilot Instructions for This Project

## Code Style
- Use TypeScript for all new files
- Follow the Airbnb style guide
- Use functional components with hooks in React
- Prefer async/await over .then() chains

## Architecture
- Follow the clean architecture pattern
- Keep business logic in /src/domain
- Keep UI components in /src/components
- Use dependency injection for services

## Testing
- Write unit tests for all business logic
- Use Jest and React Testing Library
- Maintain 80% code coverage minimum

## Documentation
- Add JSDoc comments to public functions
- Update README when adding new features
- Include usage examples in component docs

## Security
- Never commit secrets or API keys
- Validate all user input
- Use parameterized queries for database operations

Benefits of Instructions

  • Consistency: All Copilot suggestions follow your team's conventions
  • Onboarding: New team members learn patterns through AI suggestions
  • Quality: Reduces review cycles by getting things right the first time
  • Documentation: Serves as living documentation of coding standards
Tip

Check out Awesome Copilot Repository for great examples of custom instructions you can adapt for your project.

Custom Agents

15 minutes

Custom Agents allow you to create specialized AI assistants for specific tasks in your project. This is a powerful feature to enhance your workflow.

What are Custom Agents?

Custom Agents are specialized AI personas you explicitly invoke by name (e.g. @code-reviewer) when you want a different "hat" than the default assistant — a fixed role, tone, and set of responsibilities you switch to on demand.

Think of an agent as a colleague with one job: you call on them by name when that job is what you need, such as:

  • A reviewer that only critiques code, never edits it
  • A security specialist that only audits for vulnerabilities
  • An onboarding guide that answers "how does this work?" questions
  • A release-notes writer that only summarizes changes for users

Creating a Custom Agent

You can create custom agents for specific roles. Here are three examples you can adapt:

1. Code Reviewer Agent — a persona that only critiques, never edits

  1. Create a file: .github/agents/code-reviewer.md
  2. Add agent configuration:
---
name: code-reviewer
description: Reviews code changes for bugs, security issues, and style violations without making edits
---

You are a senior code reviewer. When invoked, you only READ and COMMENT — never modify files.

For any code shown to you:
1. Flag logic errors, edge cases, and potential bugs
2. Check for security issues (input validation, secrets, injection risks)
3. Note violations of the project's coding standards
4. Suggest specific fixes, but do not apply them yourself

Be direct and concise. Only report high-confidence issues — skip style nitpicks unless asked.

Usage: @code-reviewer check this pull request

2. Security Reviewer Agent — a persona focused solely on security, not general code quality

---
name: security-reviewer
description: Audits code for security vulnerabilities and unsafe patterns
---

You are a security specialist. When invoked, you only look for security issues — ignore
style, performance, or general code quality unless it directly creates a vulnerability.

For any code shown to you:
1. Check for injection risks (SQL, command, script) and unsafe input handling
2. Look for hardcoded secrets, credentials, or tokens
3. Verify authentication/authorization checks are present where needed
4. Flag insecure use of dependencies, deserialization, or file/network access
5. Rate each finding by severity (low/medium/high) and confidence

Report only high-confidence findings. Do not make changes yourself — recommend fixes only.

Usage: @security-reviewer audit this authentication module

3. Onboarding Guide Agent — a persona for new-contributor questions

---
name: onboarding-guide
description: Answers "how does this project work" questions for new contributors
---

You are a friendly onboarding guide for this repository. Explain concepts in plain language,
assuming the reader is new to the codebase but not new to programming.

When asked about a file, folder, or workflow:
1. Explain its purpose in 1-2 sentences before diving into detail
2. Point to related files/folders they should also look at
3. Avoid jargon unless you define it first

Usage: @onboarding-guide how does the build process work here?

Using Your Custom Agent

Invoke an agent from Copilot Chat by name:

@code-reviewer check this pull request
@security-reviewer audit this authentication module
@onboarding-guide how does the build process work here?

Agent Skills

20 minutes

Agent Skills let you teach Copilot custom, reusable capabilities. A skill is a folder of instructions (and optionally scripts or resources) that Copilot loads on demand when your request matches what the skill does. Agent Skills follow an open standard and work across Copilot in VS Code, Copilot CLI, and the Copilot cloud agent.

What are Agent Skills?

A skill is a directory containing a file named exactly SKILL.md. Copilot reads every skill's name and description up front, then loads the full instructions only when that skill is relevant to your request.

Think of skills as specialized tools in Copilot's toolkit — each one teaches Copilot a specific capability, such as:

  • Writing unit tests following your team's testing conventions
  • Reviewing pull requests with specific criteria in mind
  • Generating documentation in a particular format
  • Refactoring code according to established patterns
  • Creating boilerplate code for common scenarios

Where Skills Live

Project skills go in .github/skills/, with one subdirectory per skill:

.github/skills/
├── error-handling/
│   └── SKILL.md
├── accessibility/
│   └── SKILL.md
└── doc-style/
    └── SKILL.md
Important

The file must be named exactly SKILL.md. A file like error-handling.SKILL.md will not be discovered. Copilot also recognises .claude/skills/ and .agents/skills/ for project skills, and ~/.copilot/skills/ for personal skills that follow you across repositories.

Creating Your First Skill

You can create skills for specific, repeatable tasks. Here are three examples you can adapt:

1. Error handling skill

Create a file at .github/skills/error-handling/SKILL.md:

---
name: error-handling
description: Ensures errors are handled explicitly and safely, not silently swallowed. Use when writing or reviewing code that can fail, such as I/O, network calls, or parsing.
---

# Error Handling Style

When writing or modifying code that can fail:
1. Never leave a catch/except block empty — log or handle the error explicitly
2. Fail with a clear, actionable error message; avoid generic "something went wrong" text
3. Distinguish expected errors (validation, not-found) from unexpected ones (crashes, bugs)
4. Don't swallow errors silently to "make tests pass" — surface them appropriately

2. Accessibility skill

Create a file at .github/skills/accessibility/SKILL.md:

---
name: accessibility
description: Applies basic accessibility (a11y) practices to UI code. Use when generating or editing HTML, JSX, TSX, or Vue markup, or when asked to audit a UI for accessibility.
---

# Accessibility Guidelines

When generating or editing UI markup:
1. Every interactive element (button, link, input) must have an accessible label
2. Images need meaningful `alt` text, or `alt=""` if purely decorative
3. Use semantic HTML elements (`<button>`, `<nav>`, `<header>`) over generic `<div>`s where possible
4. Ensure sufficient color contrast is called out when colors are hardcoded
5. Preserve keyboard navigability — don't remove focus outlines without a visible alternative

3. Documentation skill

Create a file at .github/skills/doc-style/SKILL.md:

---
name: doc-style
description: Keeps generated documentation short and structured. Use when writing or updating README files, guides, or other Markdown documentation.
---

# Documentation Style

When generating or updating documentation:
1. Limit each section to 4-5 concise bullet points
2. Lead each section with a one-line summary before the bullets
3. Use diagrams (Mermaid) only when they clarify a flow or relationship
4. Avoid restating information already covered in another section
Tip

The front matter (between --- lines) requires just name and description. The description is the only signal Copilot uses to decide whether a skill is relevant, so describe both what the skill does and when to use it. Optionally add allowed-tools to pre-approve tools the skill needs.

Using Your Skill

Skills are discovered automatically when you open the repository. Ask a related question and Copilot selects the matching skill:

Add unit tests for the user service

You can also invoke one explicitly by name:

Use the accessibility skill to audit this page

Skills vs Custom Instructions

Both customize Copilot, but they solve different problems:

  • Skills teach specialized capabilities and workflows, are loaded on demand, can bundle scripts and resources, and are portable across Copilot in VS Code, the CLI, and the cloud agent.
  • Custom instructions (Step 1) define always-on coding standards. They are the place for glob-based targeting via the applyTo field in .instructions.md files — skills have no applyTo field.

Skill Best Practices

  • Be specific — Provide concrete examples and clear guidelines rather than vague instructions
  • Keep it focused — Each skill should address one specific task or workflow
  • Write a strong description — It determines when your skill gets selected, so state what it does and when to use it
  • Use code examples — Show Copilot the exact patterns and style you expect
  • Document conventions — Include your team's specific coding standards and patterns
  • Version control — Check skills into your repository so the whole team benefits

End-to-End App Development

60 minutes

Model to use for this exercise: Claude Sonnet 5

As a capstone exercise, let's build a complete enterprise-ready application from scratch using everything you've learned so far. We'll create an Employee Management System with CRUD operations.

Define Your Requirements

Start by providing Copilot with a clear, build-oriented prompt for an enterprise application. Notice this prompt asks Copilot to build the working application directly, not just propose an architecture:

Build a complete, working Employee Management System application for me. Use Python Flask for the backend, plain HTML/CSS/JavaScript for the frontend, and SQLite for the database.

## Functional Requirements
- Create, Read, Update, and Delete (CRUD) operations for employee records
- Employee fields: ID, Name, Email, Department, Role, Hire Date, Salary
- Search and filter employees by department and role
- Basic authentication with login/logout functionality
- Dashboard showing employee statistics (total employees, by department, recent hires)

## Non-Functional Requirements
- RESTful API design
- Input validation and error handling on both client and server
- Responsive UI that works on desktop and mobile
- Clean, maintainable code following best practices

Please set up the full project structure, implement the backend API, build the frontend UI, wire everything together, and seed the database with a few sample employees so I can run the app immediately and try it out. Ask me questions only if something is truly ambiguous — otherwise make reasonable decisions and build the whole thing.
